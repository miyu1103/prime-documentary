## 0. この仕事の目的（1文）

**検査が嘘をつくのを止める。** 作品を作るのが仕事ではない。作品を作る過程で
「緑なのに中身が違う」「終了コード0なのに何もしていない」が起きるのを、機構で止めるのが仕事。

## 1. なぜこれをやるのか（実測、2026-08-23）

PDは76話を作れる。作れないことが問題なのではない。**毎回どこかで不具合が起きる**ことが問題で、
その中身を数えると、こうなっている。

| 実測 | 値 | 出所 |
|---|---|---|
| 記録済みの罠 | 36件 | `docs/PD_CANON.md` §7 を数えた |
| 申し送り文書 | 26本 | `ls docs/handover/*.md` |
| 「計測器が嘘をついた」と明記された記録 | 7回 | handover 群と PD_CANON を grep |
| 1話あたりの作り直し回数 | EP38-50 平均3.0 → EP51-61 平均1.09 → EP62-70 平均1.78 | `08_edit/*_final_bgm.v*.mp4` の本数を話数ごとに数えた |

**不具合は「毎回違うもの」ではない。3種類が繰り返しているだけ。**

1. **黙って何もしない** — 終了コード0で成功に見えるが、意図は届いていない
2. **検査が嘘をつく** — 緑なのに中身が違う／赤なのに中身は正常
3. **並行作業の踏み合い** — 別スレが同じファイルを書き換える

**この仕事の対象は ② だけ。** ① は `scripts/pd_edit.py` と `scripts/pd_run.sh` が既に扱っている。
③ は `docs/PD_CANON.md` §3（1スレだけが触るもの）の運用問題で、別件。

## 2. 2026-08-23 に見つけた実例（これがこの仕事の見本）

`scripts/queue_unattended.sh` の `already_done()` が、
「このエピソードは完成したか」を **ファイルの更新時刻**で判定していた。

```bash
m=".../${slug}_final_bgm.v001.mp4"    # v001 を決め打ち
[ -f "$m" ] && [ -f "$f" ] && [ "$f" -ot "$m" ]   # mtime の新旧で判定
```

**両方向に間違えた。**

- 7本中6本は **v002** で出荷済み。誰も使っていないファイルを見て判定していた
- mtime は中身を何も保証しない。film.json を触るだけで答えがひっくり返る

結果、`check_queue_will_stall.py` が **5本を「無言でスキップされた＝行方不明」と報告**していたが、
7本すべて、受領書の `video_sha256` がディスク上の実ファイルと一致する＝**本当に完成していた**。
一方で「READY」と出ていた marmet は、完成・予約済みの映画を **3時間かけて作り直す**ところだった。
`queue_unattended.sh` の手動除外リスト `JOBS_HELD` は、このバグを人力で回避するためだけに存在していた。

**直し方（この形を全部に適用する）:**
`scripts/episode_is_done.py` を作り、出荷ゲートが既に正としている質問に置き換えた——
**「受領書の sha256 が、ディスク上のマスターの sha256 と一致するか」**。時刻ではなく中身。
新しい「完成」の定義は発明していない（invariant 14）。

**そのとき私自身も同じ罠を踏んだ。** 受領書は `sha256:2d368...` と書いてある。
これを裸の16進と比較すると**チャンネル全話が「不一致」**になり、大発見に見える。ただの接頭辞だった。
**あなたも必ず一度は踏む。踏んだら記録すること。**

## 3. 探すもの — 代理指標(proxy)で判定している検査

**代理指標＝「本当に知りたいこと」の代わりに、測りやすいものを測っている検査。**
以下は PD で実際に嘘をついた代理指標。全部 grep できる。

| 代理指標 | 何を偽装するか | 実例 |
|---|---|---|
| `mtime` / `-ot` / `-nt` / `st_mtime` | 「中身が新しいか」 | `already_done()`（今日修正） |
| ファイルの**存在** | 「中身が正しいか」 | 0バイトの `_finish_episode.sh` が exit 0 |
| **決め打ちのバージョン**（`v001` 直書き） | 「最新か」 | 同上。6/7話は v002 |
| **件数を数える** | 「使えるか」 | staging 177本→目視後の採用は0本 |
| **ファイル名の語** | 「中に何が写っているか」 | `woman_sitting...` が実在人物の顔だった |
| `glob("*.jsonl")` の自前集計 | 「在庫」 | 34,905点を見落とし。`shelf_rows()` を使う |
| `ps \| grep` / `kill -0` | 「動いているか」 | 検索が自分自身にヒットして誤答 |
| **ピーク値などの単一統計** | 「品質」 | 音割れ判定で法廷録音30本を誤って unusable に |
| **終了コード0** | 「意図が届いた」 | `2>&1 \| grep` がエラーを飲む |
| **カバー率＝存在を数える** | 「網羅した」 | 全部あるが全部間違い、を検出できない |
| **API応答のエコー** | 「書き込めた」 | PUT の echo でなく再取得が要る |

**探すコマンド（2026-08-23 に実際に走らせ、件数まで確認済み）:**

```bash
cd /c/Users/aab15/Documents/prime-documentary
grep -rn -- "-ot \|-nt " scripts/*.sh scripts/**/*.sh                       # A  5件
grep -rnE "(st_mtime|getmtime)[^\n]*[<>]|[<>][^\n]*(st_mtime|getmtime)" \
     scripts/ --include=*.py | grep -v test_                                # B 14件
grep -rn "_final_bgm\.v001" scripts/ | grep -v test_                        # C 51件/約12ファイル
grep -rn "ps .*grep\|kill -0" scripts/                                      # D 13件
grep -rn "2>&1 | grep\|2>&1 |grep" scripts/                                 # E  8件
grep -rn "def .*_is_done\|def already\|def .*_ready\|def .*_complete\|def .*coverage" \
     scripts/ --include=*.py | grep -v test_                                # F 25件
```

**幅の広い grep は使わないこと。** 最初に書いた `grep -rn "v001\.mp4\|v001\.json"` は
**1,425件**返した。`v001` はこのリポジトリの正当な命名規約なので、ほぼ全部が誤検知になる。
上の C のように `_final_bgm.v001`（マスターのバージョン決め打ち）に絞ると51件になり、実用になる。

**ヒット件数がそのまま作業量ではない。** 2026-08-23 に別の監査が
`out_path` という**変数名**を拾って36件中34件を誤検知している。**必ず1件ずつ中身を読む。**

**すでに分かっている有力な手がかり（C の中）:**
`scripts/check_final_acceptance.py` が `_final_bgm.v001` を持っている。
これは**受入検査そのもの**で、もし v001 を決め打ちで測っているなら、
**v002 で出荷した6本について「別の映画を測った受領書」を出している可能性がある。**
断定はしていない — まだ中身を読んでいない。**最初にここを読むこと。**

## 4. 手順（この順で。飛ばさない）

### フェーズA — 棚卸し（**変更禁止**・読むと測るだけ）

1. §3 のコマンドを全部打ち、候補を集める
2. 候補1件ずつについて、次の3つを書く。書けないものは候補から外す
   - **この検査は、本当は何を知りたいのか**（1文）
   - **代わりに何を測っているのか**（1文）
   - **どうズレるか**（具体的な入力を1つ。「ズレる可能性がある」は不可）
3. **被害の大きさで並べる。** 大きい順は次の通り（PDの実績に基づく）
   1. **無言で工程を飛ばす**（エピソードが消える。誰も気づかない）
   2. **GPU時間を捨てる**（1レンダー3時間。既に2回発生）
   3. **出荷判定を誤らせる**（BANリスク・虚偽タイトル）
   4. 表示が紛らわしいだけ（直さなくてよい場合がある）
4. 成果物：`docs/PD_INSTRUMENT_AUDIT.v001.md`
   — 表1枚（検査名 / 何を知りたい / 何を測っている / どうズレる / 被害順位 / 直すか否か）
   — **「直さない」も結論として書く。** 全部直すのは目的ではない

**フェーズAが終わったら、いったん止めてオーナーに表を見せる。** 勝手にBへ進まない。

### フェーズB — 置き換え（上位のみ）

被害順位の上から、**1件ずつ**。まとめてやらない。

1. **既存の正しい判定を探す。** 新しい定義を発明しない（invariant 14）。
   例：「完成したか」は出荷ゲートが既に `video_sha256` の一致で定義している。それを使う
2. 置き換えを実装する。**編集は必ず `scripts/pd_edit.py` を通す**（rule 4.5）
3. **わざと悪い入力で落ちることを実演する。**
   落ちるところを見ていない検査は飾り（`docs/HANDOVER.md` 恒久規則5）
4. **回帰テストを `tests/` に足す。** ただの正常系ではなく、
   **「昔の形に戻ったら落ちる」テスト**を必ず1つ入れる。例：
   ```python
   assert "-ot " not in body, "already_done が mtime 比較に戻っている"
   assert "v001.mp4" not in body, "バージョンを決め打ちに戻している"
   ```
5. **どちらに倒すかを決めて、理由を書く。** 判定に迷ったときの既定を明示する。
   PDの原則：**「わからない」なら作業する側に倒す。** 黙ってスキップする方が高くつく
6. 1件ごとにコミットする。まとめない

### フェーズC — 記録

- 新しく踏んだ罠は `docs/PD_CANON.md` §7 に**1行**足す。別の申し送りを作らない
- `docs/handover/2026-MM-DD.md` を書き、`docs/HANDOVER.md` 末尾のリンクを差し替える
- **`docs/` に段落を足して終わりにしない。** 直したなら、それはツールとテストに入っているはず

## 5. 「直った」の判定基準

次を全部満たしたときだけ「直った」と言ってよい。1つでも欠けたら言わない。

- [ ] その検査が、**わざと悪い入力で落ちるところ**を実際に見た（出力を貼る）
- [ ] その検査が、**正常な入力で通る**ところも見た（片方だけでは不十分）
- [ ] `tests/` に、**昔の形に戻したら落ちる**テストがある
- [ ] 実データ全件に対して走らせ、**結果が説明できる**（説明できない行が1つでもあれば未完）
- [ ] 判定に迷ったときの既定と、その理由が**コード内のコメントに**書いてある

## 6. 絶対にやってはいけないこと

1. **走っているシェルスクリプトを編集しない。** bash はバイトオフセットで読む。
   実行中に書き換えると残りがゴミになる。編集前に必ず確認：
   ```
   powershell -NoProfile -Command "@(Get-CimInstance Win32_Process | Where-Object { \$_.CommandLine -like '*<script>*' -and \$_.CommandLine -notlike '*Get-CimInstance*' }).Count"
   ```
2. **しきい値・宣言値・schema を緩めない**（CLAUDE invariant 15）。
   通らないなら数字を添えて報告し、オーナーの判断にする
3. **レンダー中に重い処理を走らせない**（`docs/PD_CANON.md` §4）。
   同じディスクを叩く並行作業で、長尺3本がエラーを1行も残さず死んだ
4. **実験中の動画に触らない。** タイトルもサムネイルも。
   確認：`py -3.11 scripts/pd_experiments.py --locks title`
5. **目視QCを「自動化」しようとしない。** 顔の自動検出は測定済みで使えない
   （`docs/PD_CANON.md` §7 20d）。ここは削減対象ではない
6. **`git add -A` しない。** `runs/` と SSD 素材はコミットしない
7. **オーナーに「どのコマンドで測った？」と聞かせない。** 数字には必ず出所を書く

## 7. 規律（違反したら成果物として不成立）

1. **数字には必ず出所を書く。** 出所を書けないものは「測っていません」と書く
2. **計測器を疑う。** 数字を使う前に「それは何を数えたのか」を確認する。
   **この仕事は、計測器を疑うこと自体が本体である**
3. **結論ごとに反論を1行書く。** 「この結論が間違っているとしたら、なぜか」
4. 「たぶん」「はず」「思われる」を使わない。確信が低いなら**【未検証】**と書く
5. 見つからなかったものは「見つからなかった」と書く。空欄の方が役に立つ
6. 他のセッションの「検証しました」を信じない。**誰がどのコマンドで取得したか**まで問う
   （URLごと捏造された検証報告の実例がある）
7. **自分が踏んだ罠は必ず書く。** 私は今日 `sha256:` の接頭辞で全話「不一致」と出した

## 10. 止まる条件・エスカレーション

- **フェーズAの表ができたら止まる。** オーナーに見せてから B に進む
- **既存の判定が見つからず、新しい定義を発明することになったら止まる。**
  それは設計判断であって監査ではない。オーナーに上げる
- **直すと出荷経路が変わる場合は止まる。** `.claude/rules/19-ship-gate.md` の4クラス
  （実在人物 / 権利 / 事実 / 偽造記録）に触れる変更は、オーナーの承認が要る
- 3時間以上かかりそうなら、そこまでの表を出して一度切る
