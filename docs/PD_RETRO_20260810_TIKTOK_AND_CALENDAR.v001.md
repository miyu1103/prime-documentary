# 振り返り — TikTok再構築と配信カレンダー（2026-08-09 / 08-10）

このスレで何が起きたかを、良かったことも失敗も全部書く。次のスレはここを読んでから触ること。

---

## 0. 一行で

TikTokのカバー（サムネイル）を付け直すためにアカウントを作り直し、その過程で**「ログが成功と言っても、効いているとは限らない」**という同じ形の失敗を4回踏んだ。全部、実物を見に行って初めて分かった。

## 1. 自分の失敗（重い順）

### 1.1 「13本消す」と言って137本消した ★最重要

削除ツールが予約済みを**日付チップで判定**していた。公開済みの行にも日付は出る。
`--scheduled` を付けた1回の掃引でアカウント全体が消えた。

- **被害**: 実質ゼロ。削除ログの実測で**137本すべて再生数0**。視聴のある動画は1本も失っていない。
  オーナーの「必要ならすべて消して再アップロードしてでも」という指示の範囲内でもあった。
- **問題**: 説明した手順と実際の動作が違った。オーナーは「13本」と聞いていた。
- **修正**: 予約済みは**編集アイコンが無効（`cursor: not-allowed`）かどうか**で判定する。
  それが実際に両者を分けている性質。日付は分けない。
- **教訓**: 破壊的操作の対象選択は、「たまたま相関する属性」ではなく**定義的な属性**で書く。
  そして実行前に対象件数を数えて突き合わせる（今回は数えていなかった）。

### 1.2 「cover set」というログが何も保証していなかった

カバー設定のログは**ボタンを押したこと**しか記録していなかった。2回の実行が
「成功」を報告し、実際のタイルは動画のフレームのままだった。

- **修正**: カバー画像の `src` を保存の前後で読み、変わっていなければ `COVER_DID_NOT_STICK` で止める。
- **教訓**: ログに書くのは「やったこと」ではなく**「変わったこと」**。
  副作用を主張するなら、その副作用を読み返す。

### 1.3 アップロード完了前にカバーを設定していた

TikTokの編集画面は**アップロード57%の時点で出る**。そこでカバーを入れても、
動画の処理が終わった瞬間にTikTok側の自動フレームで上書きされる。

- **修正**: `アップロード完了` の表示を待ってからカバーを設定する。
- **教訓**: 「UIが操作できる＝サーバー側の準備ができている」ではない。

### 1.4 「予約中はタイルが動画フレームになる」と断定した（誤り）

公開プロフィールのタイルだけを見て結論を出した。実際は**Studioの一覧のサムネイルが正**で、
そこにはカバーが正しく付いていた。公開グリッドは反映が遅れるだけ。

- **代償**: 2時間。存在しない不具合を追いかけた。
- **教訓**: 2つの証拠が食い違ったら、**どちらが権威あるデータか**を先に決める。
  片方だけ見て理論を作らない。

### 1.5 計測器が嘘をついたのに気づくのが遅れた（3件）

| 計測器 | 嘘の内容 | 気づき方 |
|---|---|---|
| ユーザー名の空き判定 | 全候補が「使えません」 | **ありえない文字列**でも同じエラー → 実は変更制限 |
| ハッシュタグ流通量 | `#retrogaming 9` など無関係な数字 | 出力が明らかに文脈外 |
| 監視ログ | 古い実行の内容を新しい結果として通知 | ログを切り詰めた直後だった |

- **教訓**: 検出器は**必ず失敗するはずの入力**で試す。これをやったのはユーザー名だけで、
  それ以外は偶然気づいた。
- **やれたこと**: ハッシュタグは数字を出さずに「スラッグ由来のタグは定義上リーチ0」という
  **測らなくても言える論拠**に切り替えた。これは正しい判断だった。

### 1.6 Chromeを殺さずに「再起動」していた

同じ `--user-data-dir` で起動すると**既存プロセスに合流する**だけ。
劣化したインスタンスが生き残り、再起動したつもりで同じ失敗を繰り返した。

- **修正**: `taskkill /F /IM chrome.exe` を先に必ず実行する。

### 1.7 古いリビジョンのファイルを書き換えていた

台帳同期ツールが `youtube_schedule_result.v00N.json` を全リビジョン更新していた。
古いリビジョンは**その時点の事実の記録**で、書き換えてはいけない（rule 05/12）。
実害は出なかったが、出うる設計だった。

- **修正**: ショートごとに最新リビジョンだけを触る。

### 1.8 ガードの判定基準を間違えた（2回）

`fill_short_schedule.py` のデータ鮮度チェック:
1. **mtimeで判定** → 台帳を同期しただけ（新規アップロードゼロ）で「古い」と誤判定し、安全な実行を止めた
2. **動画IDで判定に変更** → 今度は公開済みのショート全部を「未知」と誤検出。
   ダンプは**非公開動画しか列挙しない**ので、公開済みが載っていないのは正常だった

- **最終形**: 「**未来の公開予定を持つ**ローカル記録のうち、ダンプに無いもの」だけを見る。
- **教訓**: ガードを書いたら、**正常時に通ること**と**異常時に止まること**の両方を実演する。
  2回とも「異常時に止まる」しか確認していなかった。

### 1.9 「195話」を把握していなかった

オーナーが前提にしていた総数を、こちらは持っていなかった。リポジトリにも記録がない。
実測は長尺65本・ショート設計186本。**知らないことを知らないと言うのは正しかった**が、
そもそも全体計画がどこにも書かれていないのが問題。

## 2. システム側で見つかった実害（自分のミスではないもの）

### 2.1 予約日が過去日 → 予約ではなく即時公開 ★

`upload_schedule_case_v001.py` のCONFIGにある `sched_utc` は手書き。
norfolk(8/7) / willingham(8/5) / morton(8/6) の3本とも、**書いた時は未来だった日付が過去になっていた**。

過去の `publishAt` はYouTubeでは予約として扱われない。**アップロードした瞬間に公開される。**
norfolkは実際に公開された（0 views・処理中の段階で別スレが非公開に戻し、8/10 12:00に再設定）。

- **修正**: `initiate_upload` が過去日を拒否する。norfolkの旧日付で実際に拒否されることを確認済み。

### 2.2 長尺とショートが同じ12:00に公開されていた

3日ぶん、長尺エピソードとショートが同じ分にフィードへ出て食い合っていた。
再配置ツールがこれを見られなかったのは、**ローカル台帳が最大11日古かった**から。

- **修正**: 12:00は長尺専用。ショートは6/9/18/21。`--avoid-occupied` が長尺の時刻を避ける。
- **修正**: `sync_short_schedule_ledger.py` で実チャンネルから台帳を同期してから計画する。

### 2.3 索引キャッシュが直前のアップロードを隠す

`yt_channel_index` はスイープ結果をキャッシュする。数分前に上げた4本が見えず、
プランナーが**既に埋まっている枠**を空きとして提示した。

- **修正**: 日次スクリプトが先にキャッシュを消す。加えて、ローカル記録が未来の公開予定を
  持つ動画はダンプに合流させる。

### 2.4 TikTokには1日あたりの投稿上限がある ★

```
コンテンツの簡易チェック  本日のチェック回数の上限に到達しました。明日またお試しください。
```

音楽の著作権チェックは緑のまま。**コンテンツチェックだけがアカウント単位・1日単位で上限**。
待っても通らない。**回避しない**——フォロワー0の新規アカウントが1晩に100本消して100本上げるのは、
この制限が捕まえようとしている動きそのもの。

### 2.5 TikTokのアップローダーはワーカーを溜め込む

動画3本で**CDPターゲット262個**。以後ページ遷移が120秒でタイムアウトし始め、
著作権チェックの表示も間に合わなくなる。

- **修正**: 3本ごとにChromeを強制終了して作り直す。落ちた場合も再構築して同じ本から再開。

### 2.6 投稿後にカバーは変更できない

予約済み・公開済みとも、Studioの編集アイコンが全部無効。
**カバーを付け直す唯一の方法は削除して再アップロード。** これが今回の作り直しの理由。

## 3. 良かったこと

- **実測してから説明した**。オーナーが「サムネイルが無いように見える」と言った時、
  仕様の説明ではなく実際のグリッドを見に行った。黒タイルの壁を確認できた。
- **嘘の成功を3回止めた**。カバー未反映のまま99本流れるところを、1本で確認して止めた。
  もし確認しなければ全部やり直しだった。
- **著作権チェックを飛ばさなかった**。「投稿に進みますか？」を押し切れば速いが、
  それはチェックを止める操作。BANを吸収できないチャンネルなので待つ方を選んだ。
- **1日上限を回避しなかった**。技術的には可能だが、それは制限の趣旨に反する。
- **ガードを実演してから信用した**。過去日ガードは実際のnorfolk旧日付で拒否されることを確認。
  鮮度ガードは壊したダンプで発火することを確認。
- **137本削除を隠さなかった**。都合の悪い事実を先に報告した。
