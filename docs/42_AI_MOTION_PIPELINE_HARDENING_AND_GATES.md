## 1. 制作ドクトリン（ツール非依存・PD全工程に適用）

このセクションは Wan でも Remotion でも DaVinci でも効く。**4原則。**

### D1. Verify, don't assume（動く ≠ 正しい）
「動いた」で止めない。**実データで端から端まで通し、出力を目視/計測して確認する。**
今夜の9バグは全て「グラフは通る/レンダーは完走する」状態で品質だけ落ちていた。

### D2. The instrument is the first suspect（驚いたら測定器を疑う）
期待と食い違う数字が出たら、**発見ではなくツール/テスト/指標の方を先に疑う**。
- PILが16bit PNGを8bitで読んで「AEは16bit不可」と誤結論しかけた（測定器の嘘）。
- テストが出力先ディレクトリを作り忘れて「0フレーム、0エラー」→「RIFEは4x非対応」と誤読しかけた。
- 拡大鮮鋭度をNEARESTもLANCZOSも同値になる無意味な指標で測った。
- 「C,O,M,B,O」が選択肢に見えた（実際は "COMBO" という型名の1文字ずつ表示）。

### D3. Gate before spend（消費の前に落とす）
3.5時間の生成を**未検証のグラフで開始したら3.5時間を失う**。だから重い処理の前に
軽い検証を必ず挟む（グラフのdry validate、AEコンプのdry-run、フレーム数の事前計算）。

### D4. Never trust a tool's "success"（成功報告を信じない）
- `TaskStop` は成功を返したのにプロセスは3本生きていた。→ プロセス一覧で実確認。
- `/free` は8.4GB解放に成功したのに速度は1秒も改善しなかった。→「解放できた」≠「効いた」。
- 成功報告ではなく**副作用（実際のVRAM・実際のフレーム・実際の再生）**を見る。

## 3. THE GATES — 今夜の失敗を1件ずつゲート化

各ゲートは **「防ぐ失敗」→「チェック内容」→「発火位置」→「合否」→「skipの代償」** で書く。
チェックは全て**機械化可能な粒度**にした。プロンプトで判断させない。

### G-GEN-1 — サンプリング数値のモデル一致（防: shift流用）
- **失敗**: A14B に 5B 用の `shift=8.0` を流用（正: 5.0）。エラーなし、質だけ低下。
- **チェック**: 使用モデルごとに、`shift`/`cfg`/`steps`/expert切替点を**公式同梱テンプレ**
  (`ComfyUI/.../comfyui_workflow_templates_json/templates/video_wan2_2_*.json`) と突き合わせ、
  一致しなければ停止。設定値は §5 のレジストリに固定し、レジストリ外の値は要明示承認。
- **発火**: 生成グラフ組み立て時（消費前）。
- **合否**: レジストリ値と一致 = pass。
- **skipの代償**: 全カット再生成（今回換算 9×24分 = 3.6h）。

### G-GEN-2 — グラフのdry validate（防: ノード配線ミス）
- **失敗**: `WanImageToVideo` の出力(0=pos,1=neg,2=latent)を取り違え、latentにCONDITIONINGを接続。
  さらに危険なパターン: サンプラーに**ノードの条件付き出力ではなく生のCLIPTextEncodeを渡す**と、
  グラフは通るのに**開始画像がサンプラーに届かず「静止画と無関係な動画」**になる。
- **チェック**: 本生成の前に **length=最小(例5)** で1回 `POST /prompt` を投げ、
  検証だけ通す。**HTTPエラー本文(node_errors)を必ず展開してログ**（握り潰し厳禁）。
  加えて「i2v系ノードの出力2(latent)がサンプラーのlatent_imageに、出力0/1がpos/negに
  繋がっているか」を接続グラフ上で静的検査。
- **発火**: 本生成の直前。
- **合否**: 検証グラフが200 かつ 配線静的検査OK = pass。
- **skipの代償**: 3.5hのGPU時間 or 全カットが開始画像無視で無駄。

### G-CAP-1 — VRAM作業セット vs フレーム数（防: 速度見積もり崩壊）
- **失敗**: 「15-25分/カット」と見積もり→実測73分。原因はSDXLキャッシュではなく
  **フレーム数**。81フレームだと中間データ(activation)がVRAMを食い、14Bの重みが
  8.2GBしか載らず5.5GB CPU退避→毎ステップPCIe転送。41フレームなら完全ロードで24分。
- **チェック**: 生成前に想定フレーム数で**モデルが完全ロードされるか**を判定。
  起動直後のComfyログ `loaded completely` / `loaded partially` を読む。partial なら
  フレーム数を落とすかカット分割。RTX4090(24GB)/A14B-fp8 の実測境界: **≤41フレーム@720p で完全ロード、
  81フレームで部分ロード（3倍遅くなる）**。
- **発火**: 生成キュー投入前 + 1カット目完走後にログ確認。
- **合否**: `loaded completely` = pass。
- **skipの代償**: 見積もりが3-4倍外れ、夜間ジョブが朝までに終わらない。
- **設計原則**: 制約に逆らわず**短いカットを多く**する。今回は 81×5 を諦め、
  **41×9 + ヒーローはRIFE 4xでスロー化**に作り替え → 生成時間短縮かつ演出は向上。

### G-CAP-2 — ダウンロード/容量の事前計上（防: 深夜の容量切れ）
- **チェック**: 大物DL前に「回線実測 × サイズ」で完了時刻、置き場ドライブの空きを計算。
  回線は並列化で改善しない前提（今回2-6MB/s、8並列でも合計上限）。
  モデルは **D:（内蔵NVMe、空き潤沢）**、C:（空き僅少）に置かない。H:（USB外付け）は
  頻繁ロードするモデル置き場に不適。**16bitマスターは720フレームで約5.2GB**を要計上。
- **発火**: DL/レンダー開始前。
- **skipの代償**: レンダー完走直前でディスク満杯 → 成果物破損。

### G-TIME-1 — フレーム数の事前計算（防: 尺の綱渡り/黒画面）
- **失敗**: ヒーロー3.4s=164フレーム必要、RIFE 4xは41→82→164で**余裕0.8フレーム**。
  さらに検証条件が緩く(`>=150`)、**164未満でも通って末尾に黒画面が出る**状態。
- **チェック**: 各カットの `(必要フレーム = 尺 × fps)` と `(供給フレーム = 生成 × 補間倍率)`
  を**事前に算術検算**。供給 ≥ 必要 + マージン(最低3フレーム) を assert。
  補間後の実フレーム数も `-ge <実要件>` で厳密チェック（緩い閾値は禁止）。
- **発火**: タイムライン確定時 + 補間後。
- **合否**: 全カットでマージン≥3フレーム = pass。
- **skipの代償**: 最終ビートで黒フラッシュのまま出荷。

### G-TIME-2 — シーケンスのfps conform（防: 全カット早回し）
- **失敗**: AEは画像連番を**環境設定の既定30fps**で読む。conform忘れで全カット1.6倍速、
  かつ全ビートタイミングが静かにずれる。
- **チェック**: 連番取り込み後、各フッテージの `frameRate == 目標fps` を検査。
  AE: `item.mainSource.conformFrameRate = FPS` を必須化。RIFEは **f0001始まり**
  （f0000指定は「パスが無効」）なので取り込み基点も検査。
- **発火**: コンポ組み立て直後（dry-run）。
- **skipの代償**: 尺は合っているのに全カット早回しで再レンダー。

### G-COMP-1 — コンポ健全性 dry-run（防: レイヤー尺超過等）
- **失敗**: AEのソリッド/テキストは**コンプ長の尺**を持つ。`inPoint`だけ動かすと
  `outPoint`がコンプ外へ（15s コンポで title/sub/accent が out=26.6s）。
- **チェック**: 本レンダー前に**代役フッテージでコンポを構築**し、
  **全レイヤー**の `outPoint <= comp.duration` を機械検査。1件見つけて止めず全件走査。
  併せて layerごとの `motionBlur`（コンプスイッチだけでは効かない）、
  `quality==BEST`、回転は `"ADBE Rotate Z"`（2Dで `"ADBE Rotation"` はnull）を検査。
- **発火**: 本レンダー前（GPU/CPU消費前）。
- **合否**: 全レイヤー尺内 + 品質フラグ正 = pass。
- **skipの代償**: 20分×N の再レンダー、または画面外要素の無駄計算。

### G-DEPTH-1 — ビット深度の実測（防: 8bitバンディング / 測定器の嘘）
- **失敗**: 暗部ヘイズ + glow/soft-light/multiply 積層は8bit合成で必ず縞。かつ
  **PILが16bit PNGを8bitで読む**ため検証が嘘をつく。
- **チェック**:
  - 合成: `proj.bitsPerChannel=32`（float）+ RenderSetting `Color Depth: 32 bits per channel`。
  - 出力16bit: AEの**可視テンプレは全部8bit、OMの`Depth`はスクリプトread-only**。
    唯一の経路は隠しテンプレ `om.applyTemplate("_HIDDEN X-Factor 16")`
    (PNG/Trillions of Colors+/16bpc)。32bit floatは `_HIDDEN X-Factor 32`。
  - **深度検証はPIL禁止**。PNGのIHDR(byte24)直読み、または ffprobe(`rgba64be`) で確認。
  - 中間H.264を挟まない: Wan/RIFEのPNG連番をそのままAEへ（4:2:0の色間引きを合成前に入れない）。
  - 配信: 10bit HEVC マスター + 8bit H.264 互換版の二本立て（Windows標準はHEVC非対応あり）。
- **実測の効果**: 同じ暗部領域で **16bit=65万色 vs 8bit量子化=9238色（約70倍）**。
- **発火**: 出力モジュール設定時 + マスター1枚のIHDR検査。
- **skipの代償**: 暗部に縞。生成モデルを変えても直らない。

### G-OUT-1 — 最終出力の全結合検証（防: 個別OKでも結合で破綻）
- **失敗**: 今夜「各要素は個別に実証済み」でも**全部繋いだ状態の検証は最後まで一度もして
  いなかった**。
- **チェック**: 完成mp4に対し ffprobe で `duration==目標`、`r_frame_rate==目標`、
  `pix_fmt`（10bitは`yuv420p10le`/8bitは`yuv420p`）、解像度を機械検査。
  加えて末尾0.5sのフレームを抜いて**黒画面でないこと**、コンタクトシートで全カット目視。
- **発火**: エンコード直後。
- **合否**: 全項目一致 + 末尾非黒 = pass。

### G-ENV-1 — 環境の地雷（防: cp932 / bc欠如 / プロセス残留）
- **cp932**: Windowsのpython printで非ASCII（—等）が `UnicodeEncodeError`→スクリプト全死。
  **ログのprintはASCIIのみ**、または `PYTHONIOENCODING=utf-8`。
- **bc欠如**: git-bashに`bc`無し。`awk "BEGIN{...}"`。
- **プロセス残留**: バックグラウンドjob停止は**プロセス一覧で実確認しPID killを検証**。
  複数の生成チェーンが同時にGPU/出力先を奪い合う事故を防ぐ。

## 6. リソース/キャパシティ実測値（見積もりの根拠）

- A14B生成: 41フレーム@720p = **約24分/カット**（完全ロード時、4090）。81フレーム=73分（部分ロード）。
- RIFE 2x: 41→82フレームが数秒（4090）。
- AE 16bitマスター: 720フレームで **約18分**（software render）。
- エンコード: 720フレーム10bit+8bit両方で **約1分**。
- ダウンロード: 実測2-6MB/s、A14B(28.8GB)で約2.5h、並列化で改善せず（回線上限）。
- 15秒完成品(9カット)の総所要: **生成3.6h + 仕上げ0.5h ≈ 4h**（DL済み前提）。

→ PDの本編尺（数分）に外挿するときは、この単価で**カット数×24分**を先に出してから着手。

## 7. PDへの移植可否（正直な線引き）

| 要素 | 移植性 | 備考 |
|---|---|---|
| §1 ドクトリン(D1-D4) | **100%** | ツール非依存。全工程・Remotionにも効く |
| §3 の測定器/プロセス/環境ゲート | **100%** | G-DEPTH/G-TIME/G-COMP/G-ENV は合成ツール共通の罠 |
| Wan i2v の生成ゲート(G-GEN) | AI動画を使う場合のみ | PDが実写風モーションをAI生成する工程を持つなら直結 |
| A14B/SDXL の具体数値(§5) | ツール固有 | RemotionはコードモーションなのでVRAM/shift等は無関係。ただし**16bit/fps/尺検算はRemotion書き出しにも効く** |
| RIFE 48fps化 | 素材が実写風動画なら有効 | Remotionのプログラム描画は最初から任意fpsで出せる |

**要点**: PDが Remotion 一本なら §5 の数値は使わないが、**§1の4原則と、G-DEPTH/G-TIME/G-COMP/
G-OUT/G-ENV は Remotion 書き出しでもそのまま効く**（fps conform、ビット深度、尺検算、
出力検証、cp932/プロセス管理は描画エンジンに依らない）。もしPDが「実写風の被写体モーション」を
AIで足す方向に拡張するなら、G-GEN と §5 がそのまま初期値になる。
