# EP60 素材パイプライン 反省録 v001（2026-08-03）

EP60 surfside の画像279枚と実写素材選定を通して見つかった**構造的な欠陥**の記録。
「気をつける」で終わらせず、**次に同じ穴に落ちない仕組み**まで書く。

---

## A. 検索と棚について

### A-1. ゼロという結果は「棚に無い」ではなく「その言葉では届かない」

`concrete` で0/24。`cement` で0/11。`rebar` で0/1。**「劣化した鉄筋コンクリートは棚に無い」と
結論しかけた。**

言い換えたら在庫があった:

| 言葉 | 動画本数 |
|---|---|
| `bridge` | **215** |
| `abandoned` | **153** |
| `ruin` / `rust` / `demolition` / `underpass` | 53 / 51 / 50 / 49 |
| `door` | **416** |
| `stack` / `desk` / `boxes` | **308** / 256 / 111 |
| `window` / `rooftop` | **473** / 89 |

**仕組み:** ゼロが出たら、**必ず第二の語彙で測り直してから**「無い」と言う。物の名前
（concrete / rebar）ではなく、**場所の名前**（bridge / underpass / garage）で引くと当たること
が多い。

### A-2. 一つの検索語は、一つのファイル群にしか届かない

実測6例:

| 検索語 | 最大ファイル群の占有 |
|---|---|
| `concrete` | **24/24** `concrete_wall_texture_dark` |
| `column` | **24/24** `bank_building_columns` |
| `boxes` | **24/24** `moving_boxes_empty_room` |
| `elevator` | 23/24 `elevator_interior_steel` |
| `stack` | 20/24 `cash_stacks_money` |
| `hallway` | 19/24 `school_hallway_empty` |

**検索は概念ではなくラベルを引いている。**ラベルが間違っていれば結果は全滅する。

**仕組み:** 目視の前に**ファイル群の種類数を数える**。1〜2種しか無ければ、その結果は
「その群の中身」であって「その概念」ではない。別の語で引き直す。

### A-3. ファイル名は中身と無関係

- `empty_parking_garage.mp4` → **つらら**、フリーマーケット、整備工場、秋の並木道
- `evidence_locker_shelves` → **セラミックタイルと皿**
- `courtroom_gavel_block_macro` の19本 → 硬貨・キーボード・食べ物・海氷、そして1本だけ団地の空撮
- `front_door_house` → スズメ・夕日・猫
- `open_safe_empty` → **EP60で最良のプールデッキ空撮**（名前から絶対に見つからない）
- `bank_vault_door` → 木の扉／`witness_stand_empty` → 廃墟の空撮

**仕組み:** **ファイル名による自動選定を設計に入れない。**コンタクトシートの目視が唯一の
判定手段。`EP60_surfside_FOOTAGE_REVIEW.v001.md` に行が無い素材は staged しない。

### A-4. 安いふるいを先に、高いふるいを後に

`documents` を目視して「これが最良」と1本選んだ**後で**、話またぎ被り検査にかけたら
**24本中22本が既出**、選んだ1本は**7話で使用済み**だった。

被り率の実測:

| 検索語 | 既出 |
|---|---|
| `documents` | **22/24** |
| `corridor` | 19/24 |
| `apartment` | 8/10 |
| `garage` | 6/24 |
| `beach` | **3/24** |
| `construction` / `crane` | **0/24** |

**仕組み:** 目視の前に `check_cross_episode_reuse.py --check-query <q>` を回す。1コマンドで
モチーフ1つを丸ごと殺せる。**ただし被りゼロ＝良い、ではない**：`construction` は被り0だが
熱帯の工事現場ばかりで画調が合わなかった。安いふるいは候補を減らすだけで、目視は省けない。

### A-5. 名前にもデータにも出ない不良が2種類ある

全4ドライブ30,113本を走査した結果:

- **縦動画 1,189本** — `AF-BG-0074__dark_cinematic_background.mp4` が 720×1280
- **HD未満 7,048本** — 全体の23%

**棚のおよそ3割は16:9のHD映画に入れられない。**

**仕組み:** `scan_video_shape.py`（結果は `VIDEO_SHAPE_SCAN.jsonl` に保存済み）。
選定の段階で参照する。

## B. 自分の測り方について

### B-1. 計測器を疑う ― エージェントを疑う前に

夜の街モチーフで、エージェントの報告した6件中5件が「存在しない」と出た。**捏造を疑った。**

原因は**私の照合コマンド**だった。シートは `night` `street` の**2語**で作られていたのに、
照合は `"night street"` の**1語**で引いていた。2語で引き直したら **6/6 一致**。

13体・84件の照合で、**捏造はゼロ**だった。

**仕組み:** 成果物が「間違っている」と判定する前に、**その成果物が作られたときと同じ条件で**
測り直す。特にクエリ・パス・バージョンの形。

### B-2. 代理指標で「確実に落ちる」と言わない

元画像の平均輝度から「`image_cut_luma` で確実に落ちる」と断定した。

実際は **EP35 hinders は元画像の72%が輝度45未満で出荷され、輝度ゲート3項目とも合格**して
いた。組み立ての過程（深度パララックス・字幕・グラフィック）で明るくなるため。

**仕組み:** 代理指標は「予言」ではなく「原因の特定を速くする道具」として使う。落ちたときに
**どの画像が原因か即座に分かる**ことに価値がある（EP34は原因特定に3レンダー浪費した）。

### B-3. 解放した隔離項目を ⛔ 行のまま残さない

⛔-02（崩落時刻）をNISTの一次資料で解放したが、表の行を `| ⛔-02 | ~~"twenty-two minutes
past one"~~ |` のまま残した。`check_script_craft.py` は **`| ⛔-NN |` 行を全部禁止語にする**
実装なので、**解放した表現を自分で再禁止した**。

**仕組み:** 解放したら**⛔ 行から物理的に出す**。別セクション（Released quarantines）に
`CT-NN` として書き直す。

## C. ゲートそのものが間違っていることがある

### C-1. `check_script_length` の帯の表に穴があった

```
>= 45分 → 55-65分
（36-44分の段が無い）      ← 40分の話がここに落ちる
>= 20分 → 27-33分
```

EP60（40分）が「27〜33分」で判定され、**どう編集しても通らない偽の赤**になっていた。

### C-2. 「語数が最も多い稿」を選ぶ実装だった

コメントに「後の稿ほど長い」とあったが、**v004 は v003 より短い**（推敲で削ったため）。
結果、**古い稿を採点していた**。

**修正:** 版番号が最大のものを選ぶ。ただし語数が最大稿の60%未満は除外（スタブ対策）。

### C-3. manifest が10話ぶん存在しなかった

EP50〜59 に `manifest.json` が無く、全部が既定の11.5〜12.5分で判定されていた。実測ナレ尺
から `runtime_band_minutes` を書き込んで解消（19話の偽の赤 → 8話）。

**仕組み:** 偽の赤を見つけたら**ゲートを直す**。データを書き換えて通すのは騙し。
残った8話（EP04・09〜15・16）は**本当に台本が短い**ので赤のままにした。
公開済み動画の実尺を YouTube API で確認したところ、**11.5分に届いていない公開動画が11本**
あった（最短9.2分）。ゲートは正しかった。

## D. 複数スレで1話を作るときの事故

### D-1. 納品済み ≠ レンダーが読める

バッチC（顔24枚）とD（40枚）が **H: にはあるがレンダー用フォルダに1枚も無かった。**
そのままレンダーしていれば **64枚が1コマも映らなかった**（毎回の同じ失敗の3番目）。

**仕組み:** 納品の検証は**レンダーが実際に読むディレクトリ**に対して行う。H: の枚数と
`remotion/public/<slug>/img` の枚数を必ず差分で出す。

### D-2. 同じ役割の素材が、違うルールで2組できる

顔素材が2組あった:

- `F001`–`F024`（バッチC・冷たい灰青・崩落描写なし）
- `P001`–`P018`（別スレ・暖色・**うち4枚が瓦礫と救助**）

P014（瓦礫の前の消防士）とP015（夜の瓦礫の上の捜索隊）は、**この映画の絶対禁止事項に
正面から抵触**していた。しかも `asset_manifest` から**108箇所参照**されていた。

**仕組み:** 1話に複数スレが入るときは、**素材の系列ごとに「どのブリーフで作られたか」を
記録**する。禁止事項はブリーフ側にあるので、系列が違えばルールも違う。

**効いた。** 13体で34モチーフ・約800枚のタイルを検証。1体でやれば数時間の作業。

**質も落ちなかった。**

  という、こちらが気づいていなかった発見を持ち帰った

**ただし全件照合は必須。** 84件を機械照合してゼロ捏造を確認している。過去に検証担当が
URLごと10件捏造した実績があるので、**「検証した」は誰が取得したかまで問う**。

## F. 次に同じことをするときの順番

1. モチーフを決める
2. **被り率を測る**（`check_cross_episode_reuse.py --check-query`）→ 20%超は捨てる
3. **ファイル群の種類数を数える** → 1〜2種なら語を変える
4. コンタクトシートを作る（`search_archive.py --sheet`）
5. **並列エージェントで目視** → 返ってきたファイル名を全件実在照合
6. 残った本数を数える → **足りない分だけ**AI画像のブリーフを書く
7. ブリーフを書いたら**露出の床を明記**（`near-black falloff` は黒つぶれを生む）
8. 納品されたら**レンダー用ディレクトリとの差分**を出す

**6が肝。**「たぶん足りない」で100枚頼むのではなく、**測ってから枚数を決める**。
EP60では34モチーフを見て「実写75本」と確定させてから、バッチE=100枚を決めた。
